# Архитектурная схема проекта Cognitive CAPTCHA

Проект реализует экспериментальную CAPTCHA-систему, которая пытается отличить человека от бота по траектории взгляда. Вместо ввода текста или выбора картинок пользователь должен смотреть на заданные стимулы в углах экрана, а программа анализирует, насколько движение взгляда похоже на человеческое.

## 2. Назначение каждого блока

### 2.1. `app/main.py` — точка входа

Этот файл запускает программу. Он создаёт объект `CognitiveCaptchaSession`, передаёт в него реализацию eye-tracker и renderer, затем вызывает `run_session()`. Благодаря такому построению сессия не привязана жёстко к конкретному источнику данных: вместо симулятора можно будет подключить реальный eye-tracker.

### 2.2. `app/session.py` — главный управляющий слой

`CognitiveCaptchaSession` — центральный orchestrator. Он не занимается математикой напрямую, а связывает остальные модули в единый сценарий. Его обязанности:

1. Взять имя целевого стимула из последовательности.
2. Получить координаты цели из `config.CORNERS`.
3. Зафиксировать время появления стимула.
4. Попросить renderer показать стимул.
5. Попросить eye-tracker собрать gaze-точки.
6. Передать gaze-точки в velocity-анализ.
7. Если динамика неправдоподобна — записать score `0.0`.
8. Если динамика прошла проверку — посчитать score стимула.
9. После всех стимулов агрегировать score сессии.
10. Вернуть `final_score`, `verdict`, список score, детали и статистику.

### 2.3. `ui/stimulus_renderer.py` — блок отображения стимулов

Renderer отвечает только за визуальное предъявление задания пользователю. Сейчас это временная консольная реализация: она печатает, куда нужно смотреть. Архитектурно это правильное разделение: логика CAPTCHA не зависит от конкретного UI, поэтому позже можно заменить консоль на полноценное окно, веб-интерфейс или pygame-отрисовку.

### 2.4. `tracking/` — блок получения траектории взгляда

Этот слой отвечает за источник данных `(x, y, t)`:

- `HumanLikeEyeTracker` генерирует синтетическую траекторию, похожую на человеческое движение взгляда.
- `DummyEyeTracker` создаёт случайное шумовое движение для тестирования.
- `eye_tracker.py` пока служит заготовкой под настоящий eye-tracker: калибровку, подключение камеры, сглаживание и возврат сырых координат.

### 2.5. `analysis/dynamics/velocity.py` — блок кинематического анализа

Этот блок преобразует последовательность координат взгляда в профиль скоростей. Для каждой пары соседних точек вычисляется расстояние, делится на разницу времени, после чего строятся агрегаты: средняя скорость, максимальная скорость и число локальных пиков.

### 2.6. `analysis/dynamics/velocity_validator.py` — блок проверки правдоподобия движения

Этот блок решает, похожа ли динамика на движение глаз. Главная идея: человеческий взгляд обычно не двигается идеально равномерно. В траектории должны быть ускорения, замедления, пики скорости и саккадоподобные участки. Поэтому валидатор отбрасывает траектории, которые слишком ровные, вообще не имеют пиков или выглядят как чрезмерный шум.

### 2.7. `analysis/scorer.py` — математическое ядро одного стимула

Это основной алгоритмический блок. Он извлекает четыре признака:

1. **Latency** — задержка реакции: через сколько секунд после появления стимула взгляд начал устойчиво двигаться.
2. **Distance error** — средняя дистанция между точками взгляда и целевой точкой.
3. **Angle error** — насколько направление фактического движения совпадает с направлением к цели.
4. **Out-of-bounds ratio** — доля точек, которые находятся вне допустимой рамки вокруг цели.

Каждый признак нормализуется в score от `0.0` до `1.0`, затем итог считается как взвешенная сумма.

### 2.8. `analysis/session_scorer.py` — агрегатор результатов сессии

Этот блок получает список score по отдельным стимулам и считает статистику всей сессии: среднее значение, стандартное отклонение и количество стимулов. По среднему score далее принимается решение, прошёл пользователь проверку или нет.

### 2.9. `config.py` — единая конфигурация

В `config.py` собраны параметры, которые управляют поведением всей программы:

- размер экрана;
- координаты целевых углов;
- длительность стимула;
- пауза между стимулами;
- размер допустимой рамки;
- пороги latency;
- веса признаков;
- threshold для итогового решения;
- последовательность стимулов.

## 3. Как блоки связаны между собой

Связь между блоками можно описать как поток данных:

```text
config.py
   │
   ├──> app/session.py получает последовательность стимулов и координаты целей
   │
   ├──> tracking/human_simulator.py получает размер экрана и параметры движения
   │
   └──> analysis/scorer.py получает пороги, веса и размеры bounding box

app/main.py
   │
   v
app/session.py
   │
   ├──> ui/stimulus_renderer.py: показать цель
   │
   ├──> tracking/*: собрать gaze_points
   │
   ├──> analysis/dynamics/velocity.py: построить velocity profile
   │
   ├──> analysis/dynamics/velocity_validator.py: проверить динамику
   │

   │
   └──> analysis/session_scorer.py: посчитать итоговый score сессии
```

Главная особенность архитектуры — `app/session.py` знает порядок действий, но не реализует детали UI, eye-tracking и математики. Эти обязанности вынесены в отдельные модули.

## 4. Поэтапная работа программы

### Этап 1. Запуск программы

Пользователь запускает `python app/main.py`. В `main()` создаются:

- `HumanLikeEyeTracker()` — источник траектории взгляда;
- `StimulusRenderer()` — механизм показа стимула;
- `CognitiveCaptchaSession(...)` — объект сессии CAPTCHA.

После этого вызывается `session.run_session()`.

### Этап 2. Подготовка последовательности стимулов

Сессия берёт список целей из `config.STIMULUS_SEQUENCE`. Сейчас это четыре угла экрана:

1. `top_left`;
2. `top_right`;
3. `bottom_left`;
4. `bottom_right`.

Для каждого имени цели координаты берутся из `config.CORNERS`.

### Этап 3. Показ одного стимула

Для текущего стимула программа:

1. Запоминает `stimulus_time = time.time()`.
2. Вызывает `stimulus_renderer.show(target_name)`.
3. Renderer сообщает пользователю, куда нужно смотреть.

`stimulus_time` нужен для расчёта latency: программа должна знать, сколько времени прошло между появлением цели и началом движения взгляда.

### Этап 4. Сбор gaze-точек

После показа стимула сессия вызывает:

```python
gaze_points = eye_tracker.collect(
    start_time=stimulus_time,
    duration=config.STIMULUS_DURATION,
    target=(target_x, target_y),
)
```

Результат — список точек:

```text
[(x1, y1, t1), (x2, y2, t2), ..., (xn, yn, tn)]
```

Каждая точка означает: в момент времени `t` взгляд находился в координате `(x, y)`.

### 4.1. Подробный разбор `HumanLikeEyeTracker`

`HumanLikeEyeTracker` — это не настоящий eye-tracker, а синтетический генератор траектории взгляда. Его задача — выдать список точек `(x, y, t)`, которые выглядят как приближённая имитация человеческого движения глаз от центра экрана к целевому стимулу.

Класс находится в `tracking/human_simulator.py` и состоит из двух частей:

1. `__init__()` — задаёт параметры симуляции.
2. `collect()` — генерирует временной ряд gaze-точек.

### 4.1.1. Назначение конструктора `__init__()`

```python
def __init__(
        self,
        reaction_delay_range=(0.2, 0.45),
        noise_level=25,
        points=25
):
    self.reaction_delay_range = reaction_delay_range
    self.noise_level = noise_level
    self.points = points
```

Параметры конструктора:

- `reaction_delay_range` — предполагаемый диапазон задержки реакции человека. В текущей реализации параметр сохраняется в объекте, но внутри `collect()` используется жёстко заданный диапазон `random.uniform(0.18, 0.45)`. Это важная деталь: архитектурно параметр уже предусмотрен, но код пока не использует `self.reaction_delay_range`.
- `noise_level` — максимальный уровень случайного шума в пикселях. Чем больше значение, тем сильнее траектория отклоняется от идеальной линии.
- `points` — количество синтетических точек, которые будут сгенерированы после начальной точки фиксации.

Идея конструктора — отделить параметры модели от самой генерации. Это позволит в будущем делать разные профили поведения: «быстрый пользователь», «медленный пользователь», «шумный пользователь», «почти идеальный бот».

### 4.1.2. Входы и выходы метода `collect()`

Метод имеет сигнатуру:

```python
def collect(self, start_time, duration, target):
```

Он получает:

- `start_time` — время появления стимула;
- `duration` — длительность окна сбора данных;
- `target` — координаты цели `(x_target, y_target)`.

Возвращает:

```text
gaze_points = [(x0, y0, t0), (x1, y1, t1), ..., (xn, yn, tn)]
```

То есть результат — дискретная траектория взгляда во времени. Каждая точка описывает положение взгляда на экране в конкретный момент времени.

### 4.1.3. Начальная точка: взгляд стартует из центра экрана

В начале метода задаётся стартовая позиция:

```python
x_start = config.SCREEN_WIDTH / 2
y_start = config.SCREEN_HEIGHT / 2
```

Математически это точка:

```text
P_start = (W / 2, H / 2)
```

где:

- `W` — ширина экрана;
- `H` — высота экрана.

Для текущей конфигурации экрана `1920 x 1080` стартовая точка будет:

```text
P_start = (960, 540)
```

Это упрощение модели: предполагается, что перед появлением нового стимула пользователь смотрит примерно в центр экрана.

### 4.1.4. Целевая точка

Далее метод распаковывает цель:

```python
x_target, y_target = target
```

Математически это точка:

```text
P_target = (x_target, y_target)
```

Например, для `top_left` цель будет `(0, 0)`, а для `bottom_right` — `(1920, 1080)`.

### 4.1.5. Задержка реакции — моделирование когнитивной паузы

```python
reaction_delay = random.uniform(0.18, 0.45)
```

Смысл: человек не начинает движение взгляда мгновенно. Между появлением стимула и началом движения есть задержка реакции. В симуляторе она выбирается случайно из равномерного распределения:

```text
reaction_delay ~ U(0.18, 0.45)
```

где `U(a, b)` — равномерное распределение на интервале `[a, b]`.

Это означает, что любое значение задержки в диапазоне от `0.18` до `0.45` секунд считается одинаково возможным. Такая модель проста, но полезна: она создаёт естественную вариативность между попытками.

### 4.1.6. Первая точка — фиксация до реакции

```python
gaze_points = []
t = start_time

gaze_points.append((x_start, y_start, t))
t += reaction_delay
```

Первая точка траектории фиксирует взгляд в центре экрана в момент появления стимула:

```text
G_0 = (x_start, y_start, start_time)
```

Затем время сдвигается на `reaction_delay`. Это означает: до начала движения взгляд как будто остаётся в исходной позиции. В текущей реализации добавляется только одна точка фиксации, а не серия неподвижных точек в течение всей задержки. Но для алгоритма latency этого достаточно, потому что следующий большой шаг произойдёт уже после задержки.

### 4.1.7. Дискретизация траектории

Основная генерация происходит в цикле:

```python
for i in range(self.points):
```

Если `points = 25`, то метод создаёт 25 точек движения плюс одну стартовую точку фиксации. Всего получается 26 gaze-точек.

Время между соседними синтетическими точками после задержки:

```python
t += duration / self.points
```

Математически:

```text
Δt = duration / points
```

Если `duration = 1.5`, а `points = 25`, то:

```text
Δt = 1.5 / 25 = 0.06 секунды
```

То есть после задержки траектория сэмплируется примерно каждые 60 миллисекунд.

### 4.1.8. Линейный параметр движения `alpha_linear`

В начале каждой итерации считается:

```python
alpha = i / self.points
```

Это нормированный параметр прогресса движения:

```text
alpha_linear = i / N
```

где:

- `i` — номер текущей точки;
- `N` — количество точек.

`alpha_linear` изменяется от `0` почти до `1`. При `i = 0` он равен `0`, при `i = N - 1` он равен `(N - 1) / N`.

Если бы использовался только этот параметр, движение было бы линейной интерполяцией:

```text
P(alpha) = P_start + alpha * (P_target - P_start)
```

То есть каждая следующая точка двигалась бы к цели с постоянной долей прогресса. Для бота такая идеально ровная траектория слишком характерна, поэтому в симулятор добавлена нелинейность.

### 4.1.9. Экспоненциальное easing-преобразование

После линейного `alpha` код делает:

```python
alpha = 1 - math.exp(-4 * alpha)
```

Математически:

```text
alpha = 1 - e^(-4 * alpha_linear)
```

Это экспоненциальная функция приближения к единице. Её свойства:

1. При `alpha_linear = 0`:

```text
alpha = 1 - e^0 = 0
```

2. При росте `alpha_linear` значение `alpha` быстро увеличивается.
3. Чем ближе движение к концу, тем меньше добавочный прирост `alpha`.
4. Функция всегда меньше `1`, но асимптотически стремится к ней.

Производная функции:

```text
d(alpha) / d(alpha_linear) = 4 * e^(-4 * alpha_linear)
```

Она убывает по мере роста `alpha_linear`. Это означает, что в начале движение быстрее, а ближе к цели замедляется. Именно это похоже на простую модель человеческой саккады: быстрый рывок к цели и последующее затухание/уточнение.

Важно: это не биологически точная модель движения глаз, а инженерная эвристика. Она нужна, чтобы траектория не была идеально линейной и равномерной.

### 4.1.10. Интерполяция координат от старта к цели

После вычисления `alpha` координаты считаются так:

```python
x = x_start + alpha * (x_target - x_start) + noise_x
y = y_start + alpha * (y_target - y_start) + noise_y
```

Без шума это классическая линейная интерполяция между двумя точками:

```text
P(alpha) = P_start + alpha * (P_target - P_start)
```

В координатах:

```text
x(alpha) = x_start + alpha * (x_target - x_start)
y(alpha) = y_start + alpha * (y_target - y_start)
```

Вектор:

```text
D = P_target - P_start = (x_target - x_start, y_target - y_start)
```

задаёт направление от центра экрана к цели. Умножение `D` на `alpha` означает, что точка движется вдоль этого направления.

Пример: если цель справа снизу, то `x_target - x_start > 0` и `y_target - y_start > 0`, поэтому обе координаты увеличиваются. Если цель слева сверху, обе координаты уменьшаются.

### 4.1.11. Шум как модель микродвижений и неточности

Перед расчётом координат задаётся масштаб шума:

```python
noise_scale = (1 - alpha) * self.noise_level
```

Математически:

```text
noise_scale(alpha) = (1 - alpha) * noise_level
```

Затем к каждой координате добавляется случайное значение:

```python
random.uniform(-noise_scale, noise_scale)
```

То есть:

```text
noise_x ~ U(-noise_scale, noise_scale)
noise_y ~ U(-noise_scale, noise_scale)
```

Смысл этой формулы:

- в начале движения `alpha` маленький, значит `1 - alpha` большое, поэтому шум сильнее;
- ближе к цели `alpha` растёт, значит `1 - alpha` уменьшается, поэтому шум затухает;
- около цели траектория становится стабильнее.

Это имитирует грубое приближение взгляда к цели и последующую стабилизацию. Человеческий взгляд обычно не движется как идеальная математическая прямая: есть небольшие отклонения, микродвижения, шум измерения и корректировки.

### 4.1.12. Итоговая формула симулированной точки

Полная формула для точки `i`:

```text
alpha_linear_i = i / N
alpha_i = 1 - e^(-4 * alpha_linear_i)
noise_scale_i = (1 - alpha_i) * noise_level
noise_x_i ~ U(-noise_scale_i, noise_scale_i)
noise_y_i ~ U(-noise_scale_i, noise_scale_i)

x_i = x_start + alpha_i * (x_target - x_start) + noise_x_i
y_i = y_start + alpha_i * (y_target - y_start) + noise_y_i
t_i = start_time + reaction_delay + i * (duration / N)
```

А сама gaze-точка:

```text
G_i = (x_i, y_i, t_i)
```

Эта формула объединяет четыре математические идеи:

1. **Дискретизация времени** — траектория представлена конечным набором точек.
2. **Векторная интерполяция** — движение идёт от стартовой точки к цели.
3. **Экспоненциальное затухание** — скорость прогресса меняется нелинейно.
4. **Случайный шум** — траектория получает естественную вариативность.

### 4.1.13. Почему такая модель похожа на человеческий взгляд

Симулятор пытается приблизить несколько свойств человеческого поведения:

- **реакция не мгновенная**: есть задержка перед началом движения;
- **движение не идеально равномерное**: экспоненциальная функция меняет скорость прогресса;
- **траектория не идеально прямая**: добавляется случайный шум;
- **к цели взгляд стабилизируется**: шум уменьшается при росте `alpha`;
- **данные дискретны**: как и настоящий eye-tracker, метод возвращает последовательность измерений, а не непрерывную кривую.

### 4.1.14. Ограничения текущей реализации

Текущая модель полезна для прототипа, но она остаётся упрощённой:

1. `reaction_delay_range` сохраняется в `__init__()`, но не используется в `collect()`.
2. Старт всегда находится в центре экрана, хотя реальный пользователь может смотреть в другое место.
3. Во время задержки реакции добавляется только одна точка фиксации.
4. Не моделируются отдельные фазы саккады и фиксации как разные режимы движения.
5. Нет физиологических ограничений по максимальной угловой скорости глаза.
6. Шум равномерный, хотя реальные измерения eye-tracker часто имеют другое распределение.
7. Нет зависимости от частоты камеры или реального sampling rate устройства.

### 4.1.15. Как можно улучшить `HumanLikeEyeTracker`

Возможные направления развития:

- использовать `self.reaction_delay_range` вместо жёстко заданного диапазона;
- генерировать несколько точек фиксации до начала движения;
- добавить отдельную финальную фазу фиксации на цели;
- заменить равномерный шум на нормальный шум `N(0, σ²)`;
- ограничивать координаты рамками экрана;
- моделировать overshoot: небольшой перелёт за цель и возврат;
- добавить параметры пользователя: скорость реакции, точность, уровень тремора;
- строить траекторию не только из центра, а из последней точки предыдущего стимула;
- сделать частоту сэмплирования явной настройкой, например `sample_rate_hz`.


### Этап 5. Генерация человеческой траектории в симуляторе

`HumanLikeEyeTracker` начинает движение из центра экрана и стремится к целевой точке. Модель содержит:

1. **Reaction delay** — небольшую задержку перед началом движения.
2. **Интерполяцию** от стартовой точки к цели.
3. **Экспоненциальное easing-преобразование** параметра движения.
4. **Шум**, который уменьшается по мере приближения к цели.

Упрощённо координата считается так:

```text
x = x_start + alpha * (x_target - x_start) + noise
 y = y_start + alpha * (y_target - y_start) + noise
```

А `alpha` преобразуется нелинейно:

```text
alpha = 1 - exp(-4 * alpha_linear)
```

Это делает движение не идеально линейным, а более похожим на быстрое приближение к цели с последующим замедлением.

### Этап 6. Расчёт velocity-профиля

Перед основным score программа проверяет динамику движения. Для каждой пары соседних точек считается:

```text
Δx = x2 - x1
Δy = y2 - y1
Δt = t2 - t1

distance = sqrt(Δx² + Δy²)
velocity = distance / Δt
```

После этого вычисляются:

- `mean_velocity` — средняя скорость;
- `max_velocity` — максимальная скорость;
- `peak_count` — количество локальных пиков скорости.

### Этап 7. Проверка velocity

Validator применяет эвристики:

1. Если `max_velocity / mean_velocity < 1.5`, движение слишком равномерное.
2. Если `peak_count == 0`, не обнаружено саккадоподобных пиков.
3. Если `peak_count > 8`, движение слишком шумное.

Если проверка не пройдена, score текущего стимула сразу становится `0.0`, потому что движение считается непохожим на глазное.

### Этап 8. Расчёт признаков одного стимула

Если velocity-проверка пройдена, включается `score_stimulus()`.

#### 8.1. Latency

Latency — время от появления стимула до начала устойчивого движения. Алгоритм ищет несколько подряд шагов, где смещение достаточно большое. Если движение началось слишком быстро, это подозрительно; если слишком поздно — тоже плохо.

#### 8.2. Distance error

Для каждой gaze-точки считается расстояние до цели, затем берётся среднее:

```text
distance_error = mean(distance(point_i, target))
```

Чем меньше средняя ошибка, тем выше score.

#### 8.3. Angle error

Берётся вектор фактического движения от первой точки к последней и вектор от первой точки к цели. Угол между ними считается через скалярное произведение:

```text
cos(angle) = dot(v_actual, v_target) / (|v_actual| * |v_target|)
angle = acos(cos(angle))
```

Если взгляд двигался в сторону цели, угол малый и score высокий. Если движение было в другую сторону, score падает.

#### 8.4. Out-of-bounds ratio

После окна latency программа проверяет, какая доля точек находится вне рамки вокруг цели. Если пользователь действительно смотрит на цель, большинство точек должно оказаться рядом с ней.

### Этап 9. Итоговый score стимула

Каждый признак превращается в значение от `0.0` до `1.0`. Затем считается взвешенная сумма:

```text
total_score =
    latency_score          * weight_latency +
    distance_score         * weight_distance +
    angle_score            * weight_angle +
    bounds_score           * weight_bounds
```

Сейчас веса равные: каждый признак даёт 25% итогового score.

### Этап 10. Повтор для всех стимулов

Сессия повторяет этапы 3–9 для каждой цели из `STIMULUS_SEQUENCE`. Между стимулами выдерживается пауза `INTER_STIMULUS_INTERVAL`.

### Этап 11. Агрегация результатов сессии

После обработки всех стимулов список score передаётся в `score_session()`. Там считаются:

```text
mean_score = mean(stimulus_scores)
stdev_score = population_standard_deviation(stimulus_scores)
```

В текущем `run_session()` финальное решение простое:

```text
verdict = final_score >= SESSION_THRESHOLD
```

То есть если средний score больше или равен порогу, пользователь считается прошедшим CAPTCHA.

### Этап 12. Возврат результата

Программа возвращает словарь:

```python
{
    "final_score": final_score,
    "verdict": verdict,
    "stimuli": self.stimulus_scores,
    "details": self.raw_scores,
    "stats": stats,
}
```

Это удобно для отладки: можно увидеть не только итог, но и score каждого стимула, детали признаков и статистику сессии.

## 5. Краткая логика принятия решения

```text
Если velocity invalid:
    score стимула = 0.0
Иначе:
    считаем latency_score
    считаем distance_score
    считаем angle_score
    считаем bounds_score
    объединяем признаки во взвешенную сумму

После всех стимулов:
    final_score = среднее значение stimulus_scores
    если final_score >= SESSION_THRESHOLD:
        verdict = True  # человек / проверка пройдена
    иначе:
        verdict = False # бот или проверка не пройдена
```

## 6. Почему архитектура удобна для развития

Текущая структура хорошо расширяется, потому что основные обязанности разделены:

- чтобы заменить симулятор на реальный eye-tracker, нужно доработать слой `tracking/`, не меняя scoring;
- чтобы заменить консольный renderer на GUI, нужно доработать `ui/`, не меняя математику;
- чтобы улучшить алгоритм принятия решения, нужно развивать `analysis/`, не меняя запуск сессии;
- чтобы менять пороги и веса, достаточно править `config.py`.

Таким образом, проект уже построен как прототип с разделением ответственности: управляющий слой, слой данных, слой отображения, слой математического анализа и слой конфигурации.
